三、实现方式对比(标注优劣)

技术点STRMhub最优方案(来源)与理由
STRM 文件内容 自建 token 短链(安全、可签名、路径不泄露) STRMhub 最佳。openStrm/QMediaSync 内嵌完整直链(易泄露、换盘需全量重生成);AutoFilm 支持多模式。
302 反代实现 Python FastAPI 中转(易维护、易扩展,大流量是瓶颈) nginx+njs(embyExternalUrl/openStrm)性能与规则能力更强:路径/UA/码率精细路由、PlaybackInfo 改写、多级缓存、内部重定向回源、转码/字幕/直播全套。STRMhub 可借鉴其路由规则与回源降级策略,但保持 Python 便于维护。
数据存储 SQLite(持久化、事务) SQLite 系(STRMhub/LitePan)优于 openStrm 的 JSON 文件(并发写竞态、重启丢任务态)。QMediaSync 默认外部 PG 门槛过高。
驱动抽象 注册表 + DriverMeta(够用) LitePan 的"最小契约 + 可选接口 + 反射表单 + 模板脚手架"最规范,新增网盘成本最低;QMediaSync driverImpl 次之。STRMhub 可引入模板化驱动脚手架。
增量策略 快照 diff(省扫描) 三方案接近(快照/缓存比对);openStrm 全量树对比最粗放。QMediaSync 的两段式流水线并发(文件/路径双调度)对万级目录最有效,值得借鉴。
任务触发 手动 + Webhook 动作链 AutoFilm 的 cron + QMediaSync 的 Emby 入库事件触发 + MP 插件的事件推送是完整组合;STRMhub 缺 cron 定时(下一步可加)。
防误删 三层保护(远端空/阈值/确认) STRMhub 最佳(openStrm 仅布尔开关,有误删风险)。
凭据安全 AES-GCM 加密存储 STRMhub 最佳;openStrm 明文 JSON、QMediaSync 环境变量均较弱。
并发与限流 AccountGate 简单限流 AutoFilm 的扫描/下载限流分离 + LitePan 的 singleflight/冷却防雪崩 + QMediaSync 三级 QPS 限速自愈,值得组合借鉴。
前端 Vue3 轻量 SPA LitePan embed+gzip 单文件部署最简;openStrm React 生态组件丰富但体积大。STRMhub 当前方案合适。

四、项目详评

1. AutoFilm(Rust) — "STRM 生成 + 追番 + 海报"三合一定时工具

  • Rust 单二进制 + alpine 部署极简;模块清晰、约 40+ 单元测试、CI 五平台
  • Alist 官方 API 封装(非 WebDAV),token 自动重登、限速、BDMV 支持、内外网地址分离
  • .strm 智能删除保护 + 状态持久化,防远端异常误清媒体库
  • 并发设计细:扫描与伴生下载限流分离、显式栈防递归爆栈
  • 无 WebUI/无 API 触发/无通知,只能 cron
  • 不做刮削/重命名(交给 MoviePilot),RSS 用正则解析较脆弱

2. LitePan(Go) — 多网盘聚合 + 全流程影视整理(最接近 STRMhub 的对手)

  • 驱动抽象最优:最小契约+可选接口+模板脚手架,10 个网盘驱动结构统一
  • 播放双模式(302 直链/代理流)+ Range/HTTP2/并行分片;Emby 反代重写 PlaybackInfo
  • 自动化流水线:整理→STRM→刮削→刷库串连;缓存 singleflight/防雪崩细节扎实
  • 单二进制 + embed 前端 + 纯 Go SQLite(CGO=0)
  • Beta 阶段;PolyForm 非商用许可;高度依赖各家非官方 API,风控波动大
  • FUSE 需特权容器;前端 embed 重型预览库体积偏大

3. MoviePilot 插件(p115strmhelper 等) — MP 生态内 STRM 一条龙

  • 全链路自动化:整理事件→STRM→刮削→刷库→302 播放,用户无感知
  • 性能强(Rust 批量 + 8 写线程,官方 20s/10 万文件);推式生活事件监控
  • 功能密度极高:分享免转存、TG 命令、MCP、WebDAV、FUSE
  • 单体过大(Rust/Python/线程/补丁混合),维护排障成本高
  • 强耦合 MP 版本,升级易破坏;插件禁用即全停;含 Sentry/分享数据上报(隐私敏感)

4. embyExternalUrl(nginx+njs) — 302 反代与播放器外链的天花板

  • 路由规则引擎最强:路径/UA/设备/码率/IP 精细路由,失败全覆盖回源
  • PlaybackInfo 改写诱导客户端直链、两级缓存预热(详情页预加载秒开)
  • 115 深度适配(webCookie/转码 m3u8/字幕)、strm 内链跟随+sign 鉴权注入
  • 服务端注入 ExternalUrls → 全官方客户端可用(含 TV 端)
  • njs 受限子集难维护、调试靠日志;配置即代码学习曲线陡
  • 深度耦合 Emby/Plex 具体 API;强依赖 Alist 生态

5. openStrm(Next.js) — 115 目录树→STRM + WebUI 的开源代表

  • 115 官方导出接口扫大目录快;RxJS+Bottleneck 限流重试完善;Telegram 集成完整
  • 单容器全栈(MIT);302 反代继承 embyExternalUrl 成熟方案
  • STRM 内嵌完整 URL、增量全量树对比无快照、防误删仅布尔开关
  • 任务态存内存(重启丢)、JSON 文件并发写竞态、无定时/Webhook、默认弱口令

6. QMediaSync(Go) — 网盘→本地 STRM 同步 + 刮削整理主力

  • 两段式流水线并发(文件/路径双调度)+ 三级 QPS 限速自愈,万级目录实战打磨
  • 全量/增量分离 + 目录树缓存;过滤规则每目录可覆盖全局(视频扩展名/最小大小/排除名)
  • 元数据双向(下载/回传网盘)、Emby 入库事件触发增量、内嵌 302
  • 需自备 115 AppID/TMDB/Fanart 等多组密钥;默认依赖外部 PostgreSQL 15
  • README 极简、测试覆盖有限、main.go 单文件 49KB 集中式

五、对 STRMhub 的启示(按优先级)

1. 加 cron 定时任务 — AutoFilm/QMediaSync 的 cron 触发,配合现有 Webhook,补齐"无人值守"能力。
2. 302 反代增强 — 借鉴 embyExternalUrl:PlaybackInfo 改写、按 UA/码率路由、失败降级回源、详情页直链预热(起播秒开)。
3. 驱动脚手架 — 借鉴 LitePan 模板化驱动:最小契约+可选接口+脚手架,新增网盘成本降低。
4. 大目录并发 — 借鉴 QMediaSync 两段式流水线与限流自愈,提升万级目录扫描性能。
5. 刮削/海报墙落地 — LitePan/QMediaSync 的 TMDB 匹配+nfo 写入方案成熟,可对照实现。
6. 播放双模式 — 302 直链失败时降级代理流(带 Range),兼容性更好(借鉴 LitePan)。
7. TG 通知 — openStrm/MP 插件的 Telegram 集成,任务完成通知用户。
